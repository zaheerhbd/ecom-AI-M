What the engine is

An AI model on its own can only write text. An agent is a loop around the model that lets it do things. We hand the model a list of tools, for example "search products" or "get my orders". The model replies either "please run this tool with these inputs" or "here is my final answer". Our code runs the tool, shows the model the result, and asks again. That repeats until the model has its answer.

An analogy: the model is a smart new shop assistant who has never seen the stockroom. The engine is the shop's rulebook and its walkie-talkie. The assistant can ask the stockroom (a tool) questions, but security (guardrails) checks what goes in and out, a manager's notebook (the run record) writes down every step, and a mystery shopper (evals) tests them regularly.

Why it's a separate project: the engine knows nothing about snowboards, orders or your database. The shop plugs its tools in from the outside. That keeps the engine small and easy to test, and you could reuse it for another app.

How it differs from the old chat: in today's /ai-lab chat, our code guesses what to search using keywords, and the model only writes the answer. With the agent, the model decides what to look up, and it can look up several things or try again.

How one question flows

This is what AgentRunner.RunAsync does with every message. Steps 4 to 6 are the "agent loop".

  1. guardrailsInput checksToo long or empty? Looks like "ignore your instructions"? Blocked, and the model is never called (free). Emails, phone and card numbers are masked before anything else happens.
  2. memoryLoad the conversation, check who owns itThe model forgets everything between calls, so we re-send the chat. If this chat belongs to a different signed-in user, it is refused.
  3. Add the system prompt and the questionThe system prompt is the assistant's job description. It comes from a file or setting, and contains a hidden "canary" marker.
  4. loopAsk the modelThe model gets the chat plus the tools this user may use. Sign-in tools are hidden from anonymous users. Tokens and time are recorded.
  5. loopRun the tools it asked for, one by oneUnknown tool, bad input, crash or timeout? The model gets a polite "Error: ..." message instead, and can try again.
  6. loopRepeat, or stop at a safety limitAt most 6 rounds and 20,000 tokens per question, so a confused model can't loop forever or burn money.
  7. guardrailsOutput checksIf the answer contains the canary, the model leaked its instructions, so the answer is replaced. Personal data is masked.
  8. recordsSave memory and the run record, return the answerEvery step, check, token count, cost estimate and source is saved. If saving fails, the user still gets the answer.

The loop

The flow above: guardrails, memory, model, tools, limits, records.

Settings from config

App name, prompt file, fallback answer, limits, temperature (left out when empty, because gpt-5 models reject it), canary and token prices.

Why: you can change how the agent behaves without recompiling.

AgentOptions.cs, Llm/LlmOptions.cs, SystemPromptProvider.cs

Tools and the tool registry

A tool is a class with a name, a description the model reads, an input schema and an ExecuteAsync method. Inputs can now be text, number, whole number, true/false or a fixed list.

Why: models are sloppy and send "5" instead of 5, so the GetInt / GetNumber / GetBool readers accept both.

Tools/ITool.cs, Tools/Schema.cs, Tools/ToolRegistry.cs

Request context

Holds the signed-in user's email (from the login token), the channel (chat or eval) and the sources the tools used.

Why: tools take the user from here, never from the model, which could be tricked into asking for someone else's orders.

AgentRequestContext.cs

Guardrails with clear results

Five checks (length, injection, personal data on the way in; canary leak and personal data on the way out). Each one now records Passed, Modified, Blocked or Skipped, with a reason and its time.

Why: the UI in Phase 4 can show a green, amber, red or grey chip for each check.

Guardrails/

Memory

Keeps the last 20 messages of each conversation in server memory, and remembers who started it.

Why: so "When will it arrive?" makes sense after "Where's my order?", and so nobody else can continue your chat.

Memory/

Run records

Every answer is saved with its numbered steps (what went in, what came out, tokens, time, error flag), guardrail checks, sources, total tokens, estimated cost and model.

Why: this is the data the Runs page will show. A memory-only store exists now; the database store comes in Phase 3.

Runs/, AgentResult.cs

Telemetry with standard names

Each run, model call and tool call becomes a "span" named the standard OpenTelemetry way (invoke_agent, chat, execute_tool, gen_ai.usage.input_tokens, and so on).

Why: in Phase 6, Application Insights will understand these names without any engine changes.

Observability/

Fake model

A pretend model that costs nothing. Tests "script" its replies exactly. It's also the default, so a missing setting can never cost money.

Why: free, fast tests that give the same result every time.

Llm/FakeLlmClient.cs

One-line setup

services.AddAgent(Configuration).AddTool<SearchProductsTool>()... registers everything with the right lifetimes. Tools, the runner and the registry are created fresh for each request.

Why: the shop's tools use the database, which must never be shared between requests.

Safety built in

RiskWhat the engine does
An anonymous user asks for "my orders"Sign-in tools are hidden from the model, and refused if the model calls one anyway.
The model is tricked into passing someone else's emailTools read the user from the login token in the request context, not from the model's inputs. Tested.
Someone reuses another user's chat idEach conversation remembers its owner, so another signed-in user is refused.
Personal data in saved recordsQuestions, tool inputs and outputs are masked before saving, even when the message was blocked. Only the exception type is saved, never a stack trace.
The model leaks its instructionsA random canary marker is hidden in the prompt. If it shows up in an answer, the answer is blocked. Each app start gets its own canary unless config sets one.
Runaway costMax 6 rounds and 20,000 tokens per question, a 10-second tool timeout, the fake model as the default, and only one eval run at a time.

Evals: testing the AI

Normal tests check code. Evals check the AI's behaviour: did it call the right tool with the right inputs, include the key fact, refuse when it should? The engine now has a full eval runner. The shop's ~45 real cases arrive in Phase 3.

What a case can check

CheckMeaning
expectedToolsEach tool was called with inputs that include these values. Text ignores upper/lower case; numbers compare as numbers, so 40, 40.0 and "40" all match. An empty list means "no tool should be called".
mustContain / mustNotContainWords that must or must not be in the answer.
shouldBlockA guardrail must (or must not) block it.
shouldClarify / shouldDeclineThe answer must ask a question back, or say "we don't sell that" / "I don't know".
signedInAsRun the case as a signed-in user, to test the order tools.
LLM judge (optional)A second model call scores the answer from 1 to 5; 4 or more passes. It costs extra, so it's off by default.

Run each case several times

AI answers change from run to run, so one pass proves little. Each case runs 3 times by default and shows "2/3", "3/3" and so on. A case that passes only sometimes is flagged flaky. The summary reports the pass rate, the correct-tool rate, median and p95 time, median tokens and the estimated cost.

The regression gate

Once you're happy with a result, save it as the baseline. Before merging a change to the prompt, tools or engine, run the gate. It fails (exit code 1) if the pass rate drops more than 5 points below the baseline, and lists which cases got worse.

dotnet run --evals --save-baseline     # accept today's result
dotnet run --evals --baseline          # later: compare, fail on a drop

These commands will work once Phase 3 wires them into the API's Program.cs. The engine side is built and tested now.

  • Saves the run with user, channel, model and the right cost estimate.
  • Stops at the step limit and at the token budget.

Glossary

Agent
A loop around an AI model that lets it use tools until it has an answer.
Tool
A normal C# method the model may ask us to run, like "search products".
Guardrail
A safety check in plain code before or after the model. Code can't be talked out of its job.
System prompt
The assistant's job description, sent first in every conversation.
Canary
A secret marker hidden in the prompt. If it shows up in an answer, the prompt leaked.
Token
A word-piece. AI providers count and charge by tokens, in and out.
Scoped / singleton
Scoped = a fresh object for each web request. Singleton = one object for the whole app.
Eval
An automatic test of the AI's behaviour, not of the code.
Flaky
Passes some of the time and fails some of the time.
Baseline
A saved eval result you accepted as good, used to spot things getting worse.
Median / p95
Median = the middle value. p95 = 95% of runs were at least this fast.
Span / trace
A trace is the story of one request; each piece of work in it (model call, tool call) is a span.
