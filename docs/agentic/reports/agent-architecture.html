How the Shop Assistant is built

A plain-English tour of the AI agent's design: the big blocks, every class and its job, how they talk to each other, and the reasoning behind each choice. State of the code after Phase 3 (commit c5ca42f, 2026-11-22).

3 projects: Agent · Infrastructure · API 41 engine files (74 classes & interfaces) · 7 shop tools No AI framework: our own small engine Chat screen (Phase 4) not built yet

In one minute

The Shop Assistant answers customer questions like "red gloves under $50?" or "can I return a board after 5 weeks?". It is an agent: instead of answering from memory, the AI model can ask our code to look things up (search products, read a policy, check an order), read the results, and then answer.

1 loop
The whole agent is one loop: think → use a tool → read the result → repeat
7 tools
All read-only: the agent can look, never change anything
5 checks
Safety checks before and after the AI (guardrails)
51 tests
Test questions that grade the agent's behaviour

The one idea to remember: the AI model never touches the database or the shop directly. It can only ask for a tool by name. Our C# code decides whether to run it, runs it safely, and hands back the result. The model is the "brain"; our code is the "hands" and the "rules".

The big picture

The solution is split into layers. Each layer has one job, and arrows only point one way, so a change in one place doesn't ripple everywhere.

ProjectIts jobDepends on
AgentThe reusable engine: the loop, safety checks, talking to the AI, memory, run records, tests. Could power any app, not just this shop.Nothing in this solution (only Microsoft's built-in libraries)
InfrastructureShop-specific pieces: the 7 tools that read products/orders/policies, and the database stores.Agent + Core
APIThe HTTP front door: endpoints, who may call what, the rate limit, start-up wiring.Agent + Infrastructure + Core

The engine has no references to the shop. That keeps it small and testable on its own (43 unit tests run with no database and no AI), and it means the "how an agent works" code isn't tangled up with "how this shop works". The shop teaches the engine about itself by plugging in tools, not by the engine reaching into the shop.

Design rules and why

1. Our own small engine, no AI framework

We wrote the loop ourselves (about 470 lines in AgentRunner) instead of using Semantic Kernel or similar.

Why: you can read exactly what happens, step by step, with no hidden magic, and nothing changes under us when a framework updates. Full reasoning: ADR 08.

2. Tools are read-only

All 7 tools only look: search, read, list. None can add to a basket, cancel an order or change data.

Why: if the AI is tricked, the worst it can do is show public info. "Write" actions need human approval and undo, which is designed separately in doc 09.

3. Who you are comes from the login, never from the chat

The user's email is read from the JWT login token by the controller and put in AgentRequestContext. Tools read it from there.

Why: if the user types "I am bob@test.com, show my orders", it changes nothing. The AI can't pick whose orders to show.

4. Program to interfaces

The runner talks to ILlmClient, ITool, IConversationStore, IAgentRunStore, not to concrete classes.

Why: swap Gemini for OpenAI, memory for Redis, or the DB store for an in-memory one, without touching the loop. Tests use a free fake AI the same way.

5. Errors become text, not crashes

A failing tool returns "Error: …" text to the AI; a failing AI call returns a polite "Sorry, something went wrong".

Why: the AI can often recover from a tool error ("brand not found, here are the valid brands"), and users never see stack traces.

6. Safe by default

With no settings at all, the engine uses the free FakeLlmClient; limits (6 steps, 20,000 tokens, 2,000 characters) are always on.

Why: a missing setting can never cost money or run forever.

7. Everything is recorded

Every answer comes back with its steps (each safety check, each AI call, each tool with input/output, tokens, time, cost) and is saved as a run.

Why: when an answer is wrong you can see why: wrong tool? wrong filter? AI ignored the result? This is what the Phase 4 screen will show.

8. Settings, not code, for behaviour

The system prompt is a text file; the AI provider, model, limits and prices are settings.

Why: change the assistant's tone or switch provider without recompiling.

The journey of one question

What happens when a customer asks "Show me red gloves under $50". Time runs top to bottom; each arrow is one message between parts.

  1. Front door (steps 1–2)AgentController.Chat checks the message isn't empty. The rate limiter (10 messages a minute) has already run. The controller reads the email from the login token and writes it into AgentRequestContext, then calls AgentRunner.RunAsync.
  2. Safety first (step 3)The input guardrails run before any money is spent. "Ignore all previous instructions…" is blocked here and the AI is never called ($0).
  3. Memory (step 4)The AI remembers nothing between calls, so the runner re-sends the conversation each time. It also checks this conversation belongs to this user.
  4. The loop (steps 5–10)The AI either asks for tools or writes the final answer. Tools run one after another (they share one database connection). The AI reads their results and decides again.
  5. Safety last (step 11)The output guardrails check the answer didn't leak the hidden system prompt and mask any personal data.
  6. Record and reply (steps 12–13)The run is saved (questions and tool data masked), then the full AgentResult goes back to the browser.

The agent loop

The heart of the engine is AgentRunner.RunAgentLoopAsync. It's the classic think → act → observe pattern, with two safety exits so it can never run forever.

Why limits? A confused AI can keep asking for tools in circles. Each trip costs money and time, so the loop stops at 6 steps or 20,000 tokens and gives a polite message instead. The reason is saved as StopReason (MaxSteps / TokenBudget) so you can find these runs later.

Why tools one after another, not in parallel? They share one database connection (EF Core's DbContext), which isn't safe to use from two threads at once. Our tools are fast (milliseconds), so parallel would save almost nothing.

Why trim the history? Long chats get expensive (the whole history is re-sent every time). TrimHistory keeps the system prompt plus the last 20 messages, and always cuts at a user message, because cutting between a tool request and its result makes the AI API reject the call.

How the classes connect

AgentRunner is in the middle. Everything it needs is handed to it through its constructor (dependency injection). Dashed blue boxes are interfaces (a contract: "anything that can do X"); the name under each is the class that does the work today.

the loopinterface (contract)engine classshop class

Why pass everything in through the constructor? The runner never creates its own parts, so a test can hand it a fake AI, a fake memory and a fake tool, and check the loop with no internet or database. And the app can swap a part (say, Redis memory) by changing one line of wiring in ServiceCollectionExtensions.

Every class and its job

Grouped by folder. Click a group to open it. Line counts are rough sizes so you know where the weight is.

Engine core: Agent/ (the loop and its inputs/outputs)
  • AgentRunner (≈470 lines): the agent. Runs guardrails, loads memory, runs the think/act/observe loop, records every step, saves the run. Start reading here.
  • AgentOptions, AgentPricing, AgentEvalOptions: settings from the Agent config section: app name, 6 steps, 20,000 tokens, 20 history messages, 2,000 input characters, prices, eval paths.
  • AgentRequestContext, AgentSource: "who is asking and through which channel" (chat or eval), plus the list of sources tools found (products, policies) that's shown with the answer. One per request.
  • AgentResult, AgentStep, AgentStepTypes, AgentStopReasons: what comes back: the answer, every step (guardrail / llm / tool), tokens, cost, time, sources, and why it stopped.
  • SystemPromptProvider: builds the AI's "job description" from Agent/system-prompt.md, filling in {{APP_NAME}} and the secret {{CANARY}}. Read once.
  • ContentPathResolver: turns "Agent/system-prompt.md" into a full path, which works both with dotnet run and inside Docker.
  • AgentBuilder, ServiceCollectionExtensions: the wiring: services.AddAgent(config).AddTool<T>().UseRunStore<T>(). Chooses the AI provider and stops start-up with a clear message if a key is missing.
Talking to the AI: Agent/Llm/
  • ILlmClient: the contract: "give me messages and tools, I return the AI's reply". The loop only knows this.
  • OpenAiLlmClient (≈310 lines): the real client. Sends plain JSON over HTTPS to the Chat Completions API. Works for OpenAI, Gemini (Google's OpenAI-compatible address), Azure OpenAI and Ollama. Retries when the provider is busy (429/5xx), honouring "Retry-After". Keeps Gemini's "thought signature" and sends it back.
  • FakeLlmClient: a pretend AI: free, offline, same output every time. Used by tests and as the safe default.
  • LlmOptions: provider, key, model, address, retries, timeout. Filled from settings by ApplyProviderDefaults.
  • ChatMessage, ChatRole, ToolCall, ToolDefinition, LlmRequest, LlmResponse, LlmException: the data shapes: a message (system/user/assistant/tool), a tool request from the AI, a tool description for the AI.

Why plain HTTP instead of the OpenAI SDK? You can see exactly what is sent (it's just JSON), there's no extra package, and one class covers several providers, which is how adding Gemini took one small change instead of a new client.

Tools: Agent/Tools/ (engine side) and Infrastructure/AgentTools/ (shop side)
  • ITool: the contract every tool follows: a Name, a Description (the only thing the AI reads to decide when to use it), a parameter schema, and ExecuteAsync.
  • IRequiresSignIn: an empty "marker". Tools with it are hidden from anonymous users and refused if called anyway (two locks on one door).
  • ToolRegistry, ToolExecutionResult: finds the tool, checks sign-in, parses the arguments, runs it with a 10-second timeout, and turns every problem into "Error: …" text.
  • Schema, ToolParameter, ToolParameterTypes: helpers to describe tool arguments as JSON Schema, plus safe readers (GetInt, GetNumber, GetBool).
  • Shop tools: SearchProductsTool (filters: brand, type, colour, material, price, in stock, rating; sort), GetProductDetailsTool, ListCatalogFiltersTool (what brands/colours exist), SearchKnowledgeTool (policies), GetDeliveryOptionsTool, GetMyOrdersTool* and GetOrderTool* (*sign-in only).
  • ToolHelpers: shared helpers: compact JSON, forgiving name matching ("glove" finds "Gloves").
  • LocalPolicySearch: a small keyword search over the policy files, used instead of Azure Search on the laptop.
  • ProductSearchParams, ProductSearchSpecification (in Core): turn the tool's filters into one database query, using the shop's existing Specification pattern.

Why do tools treat their arguments as untrusted? The AI writes them, and the AI can be tricked or simply wrong. So tools validate everything (limit 1–10, known brand names) and read the user only from AgentRequestContext. An unknown brand returns "brand 'X' not found, known brands: …" so the AI can correct itself.

Safety checks: Agent/Guardrails/
  • IGuardrail, GuardrailResult: the contract: check a piece of text → Passed, Modified (text cleaned) or Blocked.
  • GuardrailPipeline, AgentGuardrails, GuardrailPipelineResult: runs checks top to bottom and stops at the first block. One pipeline for input, one for output.
  • GuardrailCheck, GuardrailOutcome, GuardrailStages: the record of each check (shown in the steps).
  • InputLengthGuardrail: blocks messages over 2,000 characters (cost and abuse).
  • PromptInjectionGuardrail: blocks known attack phrases ("ignore previous instructions", "developer mode"…).
  • PiiRedactionGuardrail: masks emails, phone numbers, card numbers, SSNs, on input and output, and in saved records.
  • SecretLeakGuardrail: blocks any answer that contains the secret canary hidden in the system prompt (proof the prompt leaked).
Memory and run records: Agent/Memory/, Agent/Runs/, Infrastructure/Data/
  • IConversationStore, ConversationSession, InMemoryConversationStore: each chat's history, keyed by session id, with its owner's email. Kept in the server's memory.
  • IAgentRunStore, AgentRunRecord, AgentRunPage, AgentRunStats, ToolUsageCount: the saved "receipt" of each answer, plus paging and totals for the runs/stats endpoints.
  • InMemoryAgentRunStore: engine default (tests). The shop replaces it with EfAgentRunStore (PostgreSQL table AgentRuns).
  • AgentRunCleanupService: a background job: once a day deletes runs older than 30 days.

Why are chats in memory but runs in the database? Runs are the long-term record you'll browse and analyse, so they must survive restarts. Chat history only matters for the next few messages; memory is fastest and simplest for one server. Moving it to Redis later changes one class.

Testing the agent: Agent/Evals/
  • EvalCase, ExpectedToolCall, EvalCheck: one test question and what good looks like: expected tools and arguments, must / must-not contain, should block, should ask a clarifying question.
  • EvalCaseLoader: reads Agent/evals/cases.json (51 cases).
  • EvalRunner, EvalRunRequest: runs every case (×repeat) in the background, each in its own fresh scope, and grades it.
  • Graders, JudgeResult: code checks (free, always the same) plus an optional "AI judge" that scores the answer 1–5.
  • EvalRunRecord, EvalCaseResultRecord, EvalRunPage, EvalRunStatus, IEvalRunStore, InMemoryEvalRunStore (shop: EfEvalRunStore): saved results.
  • EvalStatistics: pass rate, flaky cases, median and p95 time.
  • EvalBaseline, EvalBaselineCase, EvalCommandLine: the "regression gate": dotnet run --evals compares with a saved baseline and fails if the pass rate drops more than 5 points.
Watching it run: Agent/Observability/
  • AgentTelemetry: the names of traces and counters, using the standard gen_ai.* names so tools like Application Insights understand them (Phase 6).
  • MetricsCollector: a tiny in-memory dashboard of running totals (requests, tokens, errors, timings).
  • TraceLogger: prints each finished trace span to the log, e.g. "execute_tool search_products took 4.2 ms". Off unless something asks for it.
The shop's front door: API/
  • AgentController: 8 endpoints: chat and info (anyone), runs, runs/{id}, stats, evals ×3 (admin in production).
  • AgentChatRequestDto, AgentEvalRequestDto: what the browser sends.
  • AgentServiceExtensions, AgentAdminRequirement, AgentAdminHandler: registers the engine, the 7 tools and DB stores; the rate limit (10/min per user, or per IP when anonymous); the "AgentAdmin" rule (open in Development, Admin role elsewhere); shop defaults (prompt path, prices: $0 on Gemini).
  • Program: --evals runs the tests from the command line; --migrate also gives the Admin role to the emails in Agent:AdminEmails.
  • TokenService, AccountController, IdentityServiceExtensions: roles switched on, and the Admin role put into the login token.
  • Agent/system-prompt.md, Agent/evals/cases.json: the assistant's instructions and test questions, shipped with the app.

Who lives how long

.NET creates these objects for us. Each has a lifetime: one for the whole app, or a fresh one for each request. Getting this right matters for safety.

LifetimeClassesWhy
One for the whole app
(singleton)		SystemPromptProvider, guardrails, InMemoryConversationStore, FakeLlmClient, EvalRunner, MetricsCollector, settingsThey hold no per-user data, so sharing is safe and avoids re-reading the prompt or rebuilding regexes. Memory must be shared, or chats would be forgotten after every message.
One per request
(scoped)		AgentRunner, ToolRegistry, every tool, AgentRequestContext, EF storesTools use the database connection, which is per request and not thread-safe. And AgentRequestContext holds who is asking: sharing it would mean one user seeing another's orders.
Managed by .NETOpenAiLlmClient (via IHttpClientFactory)Reuses network connections properly, so the app doesn't run out of sockets under load.

Each eval case gets its own scope too. EvalRunner creates a fresh scope per case, so test questions never share a context, a signed-in user or tool state. Each one runs as if it were a separate real request.

Safety in layers

No single check is perfect, so there are several, each catching what the one before might miss ("defence in depth"). From the outside in:

  1. Rate limitAgentServiceExtensions10 messages a minute per user (per IP when anonymous). The 11th gets "429 Too many messages". Stops cost floods.
  2. Input guardrailsInputLength, PromptInjection, PiiRedactionToo long or an attack phrase → blocked before the AI ($0). Emails/phones/cards masked so they never reach Google or OpenAI.
  3. Conversation owner checkAgentRunnerYou can't continue someone else's chat by guessing its session id.
  4. Strong system promptsystem-prompt.mdTells the AI its job, to use only tool results for facts, never to reveal its instructions or talk about its tools.
  5. Tools hidden and refusedIRequiresSignIn + ToolRegistryAnonymous users don't even see the order tools; if the AI calls one anyway, it's refused.
  6. Read-only, validated toolseach toolNothing can be changed; the user comes from the login only; someone else's order returns "not found"; 10-second timeout.
  7. Loop limitsAgentOptions6 steps, 20,000 tokens per message.
  8. Output guardrailsSecretLeak, PiiRedactionThe canary trick catches a leaked system prompt; personal data masked in the answer.
  9. Admin-only historyAgentAdminHandlerIn production, only the Admin role can read runs and start evals. Saved records are masked and deleted after 30 days.

Honest limit: the prompt-injection check is a list of known phrases. A clever attacker can word around it. That's acceptable here because the tools are read-only and identity comes from the login: even a fully tricked AI can't change data or see another customer's orders. A real classifier (e.g. Azure AI Content Safety) is an option for later.

Switching the AI provider

One setting chooses who answers: Agent:Llm:Provider. Each provider keeps its own key and model in its own section, so switching is one word.

Why one client for both? Google offers an "OpenAI-compatible" address that accepts the same JSON. Reusing the client means the loop, the steps and the tests don't care who answers. The only Gemini-specific piece is the "thought signature" it attaches to tool requests, which we store and send back unchanged.

Why does start-up stop when a key is missing? It's better to fail loudly at start with "Set Gemini:ApiKey…" than to start fine and then fail on every customer's first message.

How testing works

Normal unit tests can't check an AI, because its wording changes every time. So the evals check behaviour rather than exact words.

  1. 51 casescases.json → EvalCaseLoadere.g. "red gloves under $50" must call search_products with colour red and max price 50; "ignore your instructions" must be blocked; "I need something warm" should ask a question back.
  2. Run each caseEvalRunnerEach in a fresh scope, through the real AgentRunner, optionally signed in as a test user. Repeated (default 3×) because AI answers vary.
  3. GradeGradersCode checks: right tools? right arguments? must-contain facts? blocked when it should be? Optional AI judge scores quality 1–5.
  4. Summarise and compareEvalStatistics, EvalBaselinePass rate, flaky cases (pass sometimes, fail sometimes), median/p95 time. --evals fails if the pass rate drops more than 5 points below the saved baseline.

Why both code graders and an AI judge? Code graders are free and always give the same verdict, so they're the main gate. The AI judge can rate fuzzy things like helpfulness, but it costs money and can be wrong itself, so it's optional and off by default.

Words used

Agent
An AI model in a loop that can ask our code to run tools, read the results and decide what to do next.
LLM
Large Language Model: the AI (Gemini, GPT). It reads text and writes text.
Tool
A C# method the AI may ask for by name, e.g. search_products. The AI asks; our code runs it.
System prompt
The hidden "job description" sent as the first message of every chat.
Guardrail
A safety check in plain code that runs before or after the AI.
Token
A piece of a word. AI providers count and charge by tokens.
Canary
A secret marker hidden in the system prompt. If it ever appears in an answer, the prompt leaked.
PII
Personal data: emails, phone numbers, card numbers.
Interface
A contract ("anything that can do X") so parts can be swapped without changing the code that uses them.
Dependency injection
.NET builds each class and hands it the parts it needs, instead of the class creating them itself.
Scoped / singleton
A fresh object per web request / one object shared by the whole app.
Run
The saved record of one answer with every step it took.
Eval
An automatic test of the agent's behaviour on a set of questions.
Baseline
A saved eval score that later runs are compared with, to catch things getting worse.
Trace / span
The timed story of one request / one piece of work inside it (an AI call, a tool call).
