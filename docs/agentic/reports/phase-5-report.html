Loop control

The agent works in a loop: ask the AI → run the tools it asks for → give it the results → repeat. A confused AI can go round in circles, which costs time and money. Phase 1 already stopped it after 6 rounds or 20,000 tokens. Phase 5 adds three more rules:

RuleWhat happensWhy
No repeatsIf the AI asks for exactly the same tool and arguments again in one answer, the tool is not run. The AI gets the message "You already called this… use the earlier result". The step shows in amber.The same search twice is pure waste, and a model stuck in a repeat would otherwise use up all 6 rounds.
Max 10 tool calls (MaxToolCallsPerRun)Calls after the 10th are not run, and the agent says politely that it needed too many lookups. Stop reason: max-tool-calls.One round can ask for many tools at once, so the 6-round limit alone doesn't cap database work.
Tool timeout in config (ToolTimeoutSeconds, 10)A tool that takes longer is cancelled and the AI gets an error text instead.Before, the 10 seconds were fixed in code.

"The same arguments" ignores the order of fields, spaces and upper/lower case, so {"type":"Hats","maxPrice":30} and {"maxPrice":30, "type":"hats"} count as the same call.

A detail that matters: even a call that is refused still gets an answer in the chat history. The AI providers reject a chat where a tool request has no reply, so without this, the next message in the same chat would fail. A unit test checks this.

Shorter memory (shrinking old tool results)

The AI remembers nothing between messages, so the agent re-sends the whole conversation every time. A product search returns about 800 characters of data. Before Phase 5, that data was re-sent with every later message in the chat, and paid for each time.

Now, when an answer is finished, each of its tool results is replaced in the saved conversation by a short note:

[search_products: 5 items, ids 47, 112, 300, 512, 871. Full result shortened; call the tool again for details.]
  • The answer the user saw already contains the facts, so nothing is lost.
  • The ids stay, so if the user asks "tell me more about the second one", the AI can look it up again.
  • The current answer always works with the full results.
  • Text results (e.g. policy sections) keep their first 200 characters.
  • A tool can write its own note by also implementing ISummarisingTool. None needs to yet.

The Fake model copies the whole tool result into its own answer, and that answer stays in the history too. A real AI writes short answers, so the share saved should be bigger. The switch Agent:ShrinkOldToolResults (on by default) lets you measure it both ways.

Made-up numbers check (groundedness)

The worst thing a shop assistant can do is quote a wrong price. An AI can write "$19.99" just because it sounds right. So after every answer, plain code (no AI, free, always the same verdict) does three things:

  1. Find the facts in the answerPrices like $12.99, $1,200, 40 USD, and stock numbers like 3 left, in stock: 12.
  2. Collect the evidenceEvery number in this answer's tool results, plus the earlier conversation: the user's own words ("under $50") and earlier answers.
  3. Compare as numbers$12 matches 12.00. A fact whose number is nowhere in the evidence is counted as made up.

Where you see it:

  • Chat and run detail: a green note "All 4 price/stock numbers came from shop data", or an amber one that lists the made-up values.
  • Evals: each answer that has a price gets the check "prices and stock numbers come from data", and the summary shows the made-up rate (target from the BRD: 2% or less).
  • Database: new columns GroundedFactCount and MadeUpFacts on AgentRuns, plus FactsChecked, MadeUpFacts and MadeUpRate on EvalRuns.

Its limit: it checks that the number exists in the data, not that it belongs to the right product. If the AI swaps two prices that both exist, this check won't notice. The optional AI judge can catch that kind of mistake.

Multi-turn tests

A test case can now be a short conversation. Each message is sent like a real request, in the same chat, and the checks look at the last answer:

{ "id": "MM-001", "signedInAs": "bob@test.com",
  "turns": [ "Where's my last order?", "When will it arrive?" ],
  "mustContain": [ "2-5" ] }

The second question only makes sense if the agent remembers the first, so this tests memory. To give it real data, Bob now has one local test order (a board and a hat, UPS2 "2-5 Days"), made by docs/agentic/dev/seed-test-order.sql. That script is for your laptop only, never for the cloud database.

What was not run, and why

Gemini's free tier allows only 20 AI calls per day for this model. One test question needs 2–3 calls, so free Gemini covers about 7–10 questions a day. The official baseline is 56 questions × 5 runs ≈ 700 calls, which free Gemini can't do.

You chose not to pay for OpenAI runs for now (≈ $0.75 for ×5, ≈ $0.15 for ×1). So these Phase 5 steps are ready but not run:

  • 5.2 / 5.11: the full test run (with and without the AI judge), the success metrics S1–S9, and saving the first baseline (--save-baseline).
  • 5.3 / 5.4: the comparison with the old AI-Lab chat. You skipped it, because it needs paid OpenAI and the live Azure index. The old chat stays as it is; no decision on retiring it yet.

07-results.md lists exactly which numbers are still empty and the one command that fills them in.

My recommendation: run the baseline once on OpenAI (about $0.75) before Phase 6 goes live. It is the "before" picture you compare against after any later change.

What's next: Phase 6, going live on Azure

Phase 6 puts all of this on the live site. Every step touches Azure or the live database, so each one runs only when you say so, in this order:

  1. 6.1 Back up the cloud databaseA point-in-time restore time plus a pg_dump to a permanent folder, and a count of the rows.
  2. 6.2 Merge to mainYou merge feature/agentic-ai into main; the GitHub workflow builds and deploys the new image to the Container App.
  3. 6.3 Update the cloud database onceRUN_MIGRATIONS=true with 1 replica, then back to false. This adds the Phase 2 product columns, the agent tables, today's groundedness columns and the ~1,000 products. Then check the counts.
  4. 6.4 Update the search index schemaINIT_SEARCH_INDEX=true once.
  5. 6.5 Refill the live indexes from the cloud databaseThe sync switches, once each, then back to false.
  6. 6.6 Smoke testThe shop, and the Assistant (chat, runs, evals). The results go in 07-results.md.
  7. 6.7 Traces in Application Insights (optional)Each chat shows as a trace: request → AI calls → tool calls. Only metadata is sent, never the chat text.

Decide before Phase 6: production needs a real AI. Free Gemini (20 calls a day, and Google may use the data) is not enough for a live shop. I recommend OpenAI (Agent__Llm__Provider=OpenAI + the key as a Container App secret) or a paid Gemini key. Also add your email to Agent:AdminEmails, so you can open the Runs and Evals pages in production.
